# ステップ１

x^nを求める。
xは(-100, 100)内の実数、nは[-2^31, 2^31-1]内の整数。
0^0は入力には含まれないらしい。また結果のx^nは[-10^4, 10^4]に収まるとのこと。

最初に問題や例を見て、少数が入るのが誤差が起こりそうで怖いなと思った。
許容誤差はどれくらいだろうか。問題内には書いていなさそう。

とりあえず、最もシンプルな方法を考えると

- n = 0なら1を返す
- n > 0ならres = 1から始めてres *= xをn回繰り返す
- n < 0ならres = 1から始めてres /= xを(-n)回繰り返す

という解法は思いつく。これはO(n)になり、n=2^31の最大ケースでは2*10^9くらいのループが回り
C++など速い言語であれば1,2秒で終わるかもしれないがPythonでは100秒くらいかかってしまいそう。

これは確か2進数を使って考えると効果的にO(logn)でやれた気がする。

以下、簡単のためn > 0の場合について考える。

```
n = b[k]*2^k + b[k-1]*2^(k-1) + ... + b[0]*2^0(b[i] = 0, 1)
```

と2進数で表すことを考える。

```
x^n = x^(b[k]*2^k + b[k-1]*2^(k-1) + ... + b[0]*2^0)
    = x^(2*(b[k]*2^(k-1) + b[k-1]*2(k-2) + ...) + b[0])
    = (x^(b[k]*2^(k-1) + b[k-1]*2(k-2) + ...))^2 * x^b[0]
    = (x^(n // 2))^2 * x^(n % 2)
```

と変形できることが分かる。`x^(n // 2)`の部分は再帰的に求められて、nが半分ずつになっていくため、
再帰の深さはO(logn)となり計算量もO(logn)となり十分速くなる。

n < 0 の場合はまずx^(-n)にして最後に1/x^(-n)を返すという方法で出来そう。
上の式を割り算に変えてもいけるだろうか。

最初に以下のようなコードを書いてエラーとなった。
OverflowErrorでx = 2.0, n = -200000000というケースのときにx^(-n)をまず計算するというところで
めちゃくちゃデカい数になってしまったのだろうか。

> OverflowError: (34, 'Numerical result out of range')

```python
class Solution:
    def myPow(self, x: float, n: int) -> float:
        def pow_helper(k: int) -> float:
            if k == 0:
                return 1
            return pow_helper(k // 2) ** 2 * x ** (k % 2)

        if n >= 0:
            return pow_helper(n)
        else:
            return 1 / pow_helper(-n)
```

GPTに解説してもらうと以下のような回答を得られた。

> あなたの実装では n < 0 のときに pow_helper(-n) を計算してから 1 / ... を取っています。
> たとえば x=2, n=-200000000 のときは内部で pow_helper(200000000) を計算しようとし、
> 途中で 2**200000000 といった非常に巨大な浮動小数（≳10⁶⁰⁰⁰⁰⁰…）を作ろうとして IEEE 浮動小数の上限を越え、
> OverflowError: (34, 'Numerical result out of range') が発生します。

[IEEE 754](https://ja.wikipedia.org/wiki/IEEE_754)が浮動小数点数に関する標準規格らしい。
IEEE 754で定められた浮動小数点数の最大値を超えてしまったからOverflowErrorになってしまったということだろうか。

これだとnが負のときに割っていくようにしてもアンダーフローエラーが起こってしまう？
負のときは割り算にしたらアンダーフローは起きずに通るようになった。
うーん、浮動小数点数周りのことがよく分かってない…

もう少し調べるとどうやらべき乗演算子のときにオーバーフローが発生しているようだった。

```python
>>> float_max = 1.7976931348623157e+308 # floatの最大値
>>> float_max ** 2
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
OverflowError: (34, 'Numerical result out of range')
```

一方でちょっと書き方を変えるとオーバーフローエラーは起きずにinfが返ってくるようになった。

```python
>>> float_max * float_max
inf
```

一方でアンダーフローの場合はどうなのかというと、これはどちらの場合もエラーは起きず0を返すようだった。

```python
>>> float_min = 2.2250738585072014e-308 # floatの最小値
>>> float_min ** 2
0.0
>>> float_min * float_min
0.0
```

このあたりはIEEE754というよりCPythonの内部実装的な話だろうか。
wikiによると

> オーバーフロー（結果が正しく表現できないほど大きくなった場合） - 最近接丸めモードの場合、デフォルトでは ±∞ を返す。
> アンダーフロー（結果が正規数で表現できないほどに小さく非0であるが不正確な結果となった場合） - デフォルトでは非正規化数を返す。

改めて浮動小数点数周りの知識がかなりあやふやであることが分かった。
浮動小数点数について知っていたことは

- 符号(+/-), 指数部, 仮数部で32/64bitを分けて表現している
- bitによって表現できるのは有限のためどうしても誤差が発生する
- 誤差が発生するので避けられるならなるべく避けて必要なときだけ使うようにする、使うなら誤差を許容する

くらいの知識しかなく、infや非正規化数がどのように扱われているかなどもちゃんと分かってない。
この辺りは改めてちゃんと勉強する必要がありそうだと感じた。

少数周りの話は一旦置いて、GPTに相談した際にiterativeな解法を紹介されて気づいたが、
xを2乗していきresultを持っておくほうが分かりやすかった。というかその方が自然か。
再帰で考えるときにbottom-upばかり考えてしまうという自分の癖がありそう。

Pythonだと何も考えずに負の場合に`n = -n`とおけるが符号付き32bit整数を使っていると
n = -2^31のときにn = -nとすると範囲を超えてしまいエラーになるという問題があるようだ。
これは注意深く意識していないと気づかなさそう。

https://github.com/potrue/leetcode/pull/45/files#r2272676005

基本的に割り算は遅くビット演算は速いという話が出ていた。
C/C++はコンパイラが賢いらしいので`% 2`は等価な`& 1`に最適化されるという話があったが、
Pythonの場合はどうなのだろうか。そのあたりもCPythonのコードを当たるなりして調べてみてもいいかもしれない。

ChatGPTにも聞いてみた。
https://chatgpt.com/s/t_68f35181a1908191a30ae02a82933ad0

要約すると

- Pythonでは`% 2`を`& 1`に書き換えるようなことは行われない
- 理論的にはビット演算のほうが速いがCPythonではPyLongという任意精度整数を通るため必ずしも&のほうが速いわけではない
  - ビット演算で書き換えたほうが遅くなったというstackoverflowの報告例もある
- こういった最適化をするのであればまずベンチマークを取るべき

という話であった。
