# ステップ１

整数配列から狭義の単調増加部分列を求める

本当に愚直にやろうとすると全ての部分列を取ってそれが単調増加部分列になるかチェックするということはできるが
全ての部分列は2^N通りあるため、とても現実的な解法ではない。

- dp[i]: i番目を単調増加部分列の末尾としたときの最大長さ

として前から順番にiを動かしていって更新することを考えるとdp[0],...,dp[i-1]が分かっているとき、

- dp[i] = max(dp[j]) + 1 s.t. 0 <= j < i and nums[j] < nums[i]

と更新できることが分かる。この方法であれば各dp[i]の更新にO(N)かかるので、全体としての計算量はO(N^2)になる。
N = 2500が最大なのでN^2 = 6.25 * 10^6であり、Pythonが1秒間に10^7回の演算ができると仮定すると
各ループで2~4回の演算が行われるとしても1~2秒程度では解けそうという見積り。
とりあえず通った、計算時間も1107msで見積りの範囲内であった。

follow-upにO(NlogN)で解くことができるかという問いがあった。

- query(x): data[0],...,data[x-1]内の最大値を求める
- update(i, x): data[i] = xに更新する

という各操作がO(logM)(M:dataの個数)で出来るデータ構造があれば各ステップで

1. dp[i] = query(nums[i]) + 1
2. update(nums[i], dp[i])

とすれば全体でO(NlogM)でやれる。ただし、numsの値に幅があればあるほどdataの数も大きくなってしまうが、
今回は数値の大小だけが問題になっているので座標圧縮をして数値の大小関係のみを保持しつつnumsの値の幅を削減すると
Mが高々Nになるので全体としてO(NlogN)である。

そして、上記の条件を満たすデータ構造としてセグメント木というものがある…ということを過去にAtCoderなどをやっていたので知っていた。
（上の条件だけならBinary Indexed TreeまたはFenwick Treeというセグメント木を簡略化したものでも行けるんだったかな…
ちょっと覚えてないのであやふやです）。
https://en.wikipedia.org/wiki/Segment_tree

確かセグメント木はSWEの常識を超えていて知らなくても問題無いというのを過去ログで見たので、
ここまでやらなくてもいいとは思うが私自身の復習も兼ねて実装してみることにする。

何とか書けた。セグメント木が空で書けるかやや不安だったが、図を書いたりしてロジックを整理して書くことができた。
計算時間は152msに短縮された、O(N^2)からO(NlogN)なのでそれだけ見ると最大ケースでは100倍くらい速くなってもよさそうだが
実際はセグメント木の操作の定数倍が結構重くてこれくらいという感じだろうか。
座標圧縮を行うコードがあんまりスマートではない気がする。

また書いていて気付いたことだがmaxを取るセグメント木は今より小さい値への更新はできなかった。
今回の場合同じnums[i]に対する更新がかかったときにそれは必ず前で見たときより長い増加列を作れるはずで、
より小さい値に更新されることは無いので特に問題は無かった。

また入力の制約が`-10^4 <= nums[i] <= 10^4`なので、座標圧縮をせずに`nums[i] = nums[i] + 10^4`としても
numsの値の幅が[0, 2*10^4]になってセグメント木で取り扱える程度には小さいのでそういうやり方もあるなと思った。
ただし実務的には入力の制約は将来的に破られる可能性があることを考えると座標圧縮するほうがよさそう。

なんかこんなんあった気がするけど、なんでこれで上手くいくんだっけ…？
ああ、前から順に見て直接LISを作っていっているのか。いや違うか、例でやったらたまたまLISになったけどそうではないか。
LIS自体になるわけじゃないけど、dp[i] = valであるとき「最後がvalになる長さ(i+1)のLISを作れる」ということを

- val > dp[-1] のとき、純粋にLISの長さを増やせるのでdp.append(val)する
- そうでないときは、二分探索して`val <= dp[i]`となる最小のiを見つける。
  - LISの長さが同じなら最後が小さいほうがいいのは明らかなため、`dp[i] = val`と更新する

という一種の貪欲法が混ざっている。
