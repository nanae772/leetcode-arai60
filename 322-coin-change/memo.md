# ステップ１

何種類かの硬貨（枚数無限）を使ってちょうど金額を支払う組合せで枚数が最小になるものを求める。
ただしちょうど払える組合せが無いときは-1を返す。

まずやってしまいそうなミスとしては「最も大きいもので支払っていく」という貪欲解があり、
日本円だとうまくいくが一般的にはそうではないというのがあった記憶。
たとえば
```
coins = [1, 5, 8], amount = 10
```

という入力に対して大きいものから支払っていくと 8 + 1 + 1 で3枚になるが
実際は5 + 5なので2枚でよい。
なのでこの貪欲解は一般的には使えない。

残りx円のときの選択肢としては

1. coins[0]を使い枚数+1、残りx-coins[0]円を支払う
2. coins[1]を使い枚数+1、残りx-coins[1]円を支払う
...

なのでこれらの選択肢のうち最小の支払い枚数となるx-coins[i]が分かればよいということになる。
残金のとり得る状態がamount + 1、各状態からの遷移はコインの枚数分なので
今回のケースだとO(len(coins) * amount)の計算量になり、
`len(coins) <= 12, amount <= 10^4`の制約ではこのDPで100msもあれば解けそうという見積り。

メモ化再帰でもいいし配列を順に見ていくDPでもいいが、
今回はシンプルなので最初から配列を順に見るDPでやることにする。

解いてからそういえばこれはやっていることはほぼ個数無限のナップサック問題であるということを思い出した。
https://en.wikipedia.org/wiki/Knapsack_problem#Dynamic_programming_in-advance_algorithm

最初にamountより大きいコインは絶対使えないのでfilterしておくという処理をされていた。
確かに今回の制約だと`1 <= coins[i] <= 2^31 - 1, 0 <= amount <= 10^4`になっていたので
coinsにamountより大きいものが入ってきている可能性はあり、
特に`[1, 2^31 - 1]`の間でcoinsがランダムに生成されているような場合は大部分が不要なコインになっていそうで
そのようなケースに対しては有効に働くかと思ったが、改めて読むと`len(coins) <= 12`だったので
減ってもそんなに大幅に減るということは無いか。
しかしやっておいても損は無さそう。

BFSでやるときに気をつけないと同じ地点が複数回キューに入ることにより、サイズが指数オーダーになるという話。
自分がこのコードを読んだときにその問題点に気づけるかというと難しそう。

https://github.com/seal-azarashi/leetcode/pull/37/files#r1830471177

コインを降順に並び替えると少し速そうというのは大きい硬貨を使うほうがより速く0に到達できそうだからかな。

https://github.com/seal-azarashi/leetcode/pull/37/files#r1833630928

一方でコインを昇順に並び替えておくと超えた段階でbreakできる

https://github.com/fhiyo/leetcode/pull/24#discussion_r1648673169

intにfloat('inf')を混ぜるのはやはり違和感があるという話で、その上で使うのだったら
math.infのほうがシンプルに感じるという話。

実際BFSのほうも実装してみて、LeetCode上でしか試していないので大雑把だが

- DP: 700ms程度
- BFS: 230ms程度

となり、実際にBFSのほうが速く終わっている。

# ステップ３

速度面ではBFSのほうが優位そうだが、最終的には以下の理由によりDP解を選んでやることにした。

- 個人的にBFSよりDPで解く方が分かりやすく感じた
- DPテーブルが残るのでデバッグの際にBFSより原因調査がやりやすそう
